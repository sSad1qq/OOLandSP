# Инструкции для работы с проектом ООЯиСП

## Назначение проекта

В каталоге находятся учебные лабораторные работы по дисциплине
«Объектно-ориентированные языки и системы программирования» и учебное
пособие `Горюнов Ю.Ю., Леонова Т.Ю. ООЯиСП_Уч.пособие.pdf`.

Каждую лабораторную работу выполнять строго в рамках ее темы и варианта.
Не превращать учебное решение в универсальную библиотеку и не усложнять
архитектуру без прямой просьбы пользователя.

## Источник требований и их приоритет

При противоречиях использовать следующий приоритет:

1. Прямое требование пользователя.
2. Условие и требования нужной лабораторной работы в пособии.
3. Условие конкретного варианта.
4. Рекомендации и пример выполнения из пособия.
5. Существующий стиль исходного файла.

- Перед работой открыть в пособии раздел нужной лабораторной, а не искать
  только похожий пример программы.
- Не угадывать номер варианта по названию каталога. Определять его по
  сообщению пользователя, условию или существующему коду. Если источники
  расходятся, уточнить вариант у пользователя.
- Папки и файлы с суффиксом `K` считать теми же заданиями с другим
  вариантом, а не контрольными работами.
- Если формула или математический символ плохо извлекается из PDF,
  посмотреть отрисованную страницу. Если и после этого смысл неоднозначен,
  задать уточняющий вопрос.
- Примеры из пособия считать рекомендациями, а не безошибочным эталоном.
  В них встречаются неполное освобождение динамической памяти,
  `while (!eof())`, жестко заданные Windows-пути и смешение синтаксиса
  C++/CLI и C#.

## Текущая структура

- `lb1_1/main.cpp` - отдельная консольная программа ЛБ 1.1. Текущий код
  соответствует варианту 6, функции Мёбиуса.
- `lb1_2/main.cpp` - отдельная консольная программа ЛБ 1.2. Текущий метод
  соответствует варианту 6: поиск наименьшего элемента при простой сумме
  индексов. Перед изменениями это соответствие перепроверить.
- Файлы `lb1_1/lb1_1` и `lb1_2/lb1_2` - ранее собранные бинарники. Не
  изменять их и не использовать как доказательство корректности исходника.
- В проекте нет общей системы сборки. Каждая консольная лабораторная
  компилируется отдельно.

## Карта лабораторных работ

### Консольные работы 1.1-1.6

- **ЛБ 1.1:** класс с закрытыми полями `a`, `b`, `h`, конструктором и
  открытыми методами вычисления `f(n)` и табулирования. Нужны два
  экземпляра: обычный с параметрами по умолчанию и указатель на класс с
  явно заданными параметрами, а также отдельные тесты `f(n)`.
- **ЛБ 1.2:** класс-родитель хранит, заполняет случайными вещественными
  числами из `[A; B]` и выводит динамический двумерный массив. Класс-потомок
  решает задачу варианта. Вызовы конструкторов и деструкторов должны быть
  видны и проверены.
- **ЛБ 1.3:** шаблоны классов-родителя и потомка повторяют задачу варианта
  ЛБ 1.2. Результат требуется показать для массивов типов `int` и `float`.
- **ЛБ 1.4:** поля класса содержат входные данные; конструктор их
  инициализирует; перегруженная унарная или бинарная операция решает
  задачу; недопустимые входные данные обрабатываются исключением.
- **ЛБ 1.5:** повторить задачу варианта ЛБ 1.2 с файловыми операциями.
  Методы записи и чтения двумерного массива объявляются в
  классе-родителе.
- **ЛБ 1.6:** объявить класс, метод которого решает строковую задачу
  варианта с использованием операций и методов `string`.

ЛБ 1.1-1.6 являются отдельными программами. Не переносить в новую работу
всю реализацию предыдущей лабораторной, кроме случаев, прямо указанных
выше.

### Windows Forms 2.1-2.7

Работы 2.1-2.7 последовательно расширяют один проект:

- **ЛБ 2.1:** форма, заданный заголовок и меню с пунктом ЛБ 2.2.
- **ЛБ 2.2:** `groupBox1`, два текстовых поля и кнопка для строковой задачи;
  блок показывается через пункт меню.
- **ЛБ 2.3:** `groupBox2`, `ListBox`, интерактивный размер и вектор
  случайных целых чисел для задачи варианта.
- **ЛБ 2.4:** `groupBox3`, `DataGridView`, интерактивные размеры
  двумерного целочисленного массива, инициализация, файловый обмен и
  решение задачи варианта.
- **ЛБ 2.5:** добавить `OpenFileDialog` и `SaveFileDialog` для чтения и
  записи таблицы.
- **ЛБ 2.6:** `groupBox4`, `Chart` и `Timer` с интервалом 100 мс для
  поэтапного построения полярной кривой варианта.
- **ЛБ 2.7:** `groupBox5`, таблица, кнопки старта и остановки и таймер с
  интервалом 100 мс для моделирования случайного блуждания на `[0; 77]` с
  отражающими границами.

Не создавать ЛБ 2.2-2.7 как независимые приложения, если пользователь
прямо не попросил изменить структуру курса.

## Порядок работы

1. Прочитать запрос пользователя, текущие исходники и точный раздел
   пособия.
2. Явно определить лабораторную, вариант, обязательные элементы и
   ожидаемый результат. Не додумывать отсутствующие сведения.
3. Перед изменением кода сначала сообщить найденные проблемы и составить
   план исправления. Реализацию начинать после подтверждения пользователя.
4. Вносить только относящиеся к задаче изменения. Не форматировать и не
   переписывать весь файл без отдельной просьбы.
5. Проверить сборку, выполнение и специальные случаи варианта.
6. Раздельно сообщить, что установлено чтением кода, что подтверждено
   компиляцией и что подтверждено запуском.

## Стиль C/C++

- Сохранять учебный стиль окружающего файла и писать прямое решение без
  лишних абстракций.
- Обычные переменные называть в `camelCase`, массивы и матрицы - в
  `PascalCase`, константы - в `UPPER_SNAKE_CASE`.
- Функции называть коротко и по действию: `display`, `initFile`,
  `processMatrix` и аналогично.
- Пользовательские сообщения, подсказки и комментарии писать на русском
  языке.
- Для кириллицы в переносимой консольной программе использовать
  `setlocale(LC_CTYPE, "")`, когда это необходимо.
- Допускается существующее смешение C и C++: C-массивы, `iostream`,
  `stdio.h`, `FILE *`, `fstream`, `new` и `delete`.
- Не заменять учебные массивы, указатели и классы современными
  контейнерами или умными указателями, если пользователь не просил
  улучшить архитектуру.
- Использовать отступы окружающего файла; при создании нового файла -
  четыре пробела.
- Добавлять короткие русские комментарии только рядом с важными
  действиями.

## Обязательные проверки корректности

- Для динамического двумерного массива выделять память для каждой строки,
  а при уничтожении удалять сначала каждую строку, затем массив указателей.
- Каждому `new` должен соответствовать подходящий `delete` или `delete[]`.
- Проверять границы циклов и допустимость размеров, шага табулирования и
  входных данных.
- Явно определить, с нуля или с единицы считаются индексы в условии. Не
  менять принятую трактовку молча.
- При чтении файла проверять успешность извлечения данных; не использовать
  `while (!stream.eof())` как условие чтения.
- Подключать заголовки, непосредственно объявляющие используемые функции.
- `main` должен возвращать `0` при успешном завершении.
- Успешная компиляция сама по себе не доказывает отсутствие ошибок памяти
  или правильность алгоритма.

## Сборка и запуск консольных работ

Проверочные бинарники создавать в `/tmp`, не поверх файлов лабораторной:

```bash
c++ -std=c++17 -Wall -Wextra -Wpedantic lb1_1/main.cpp -o /tmp/oolandsp_lb1_1
/tmp/oolandsp_lb1_1
```

Для программ с указателями, динамическими массивами или файловыми
операциями дополнительно использовать санитайзеры:

```bash
c++ -std=c++17 -Wall -Wextra -Wpedantic \
  -fsanitize=address,undefined lb1_2/main.cpp -o /tmp/oolandsp_lb1_2_san
/tmp/oolandsp_lb1_2_san
```

Для конкретной лабораторной заменить путь и имя временного бинарника.
Проверить обычные случаи, граничные значения и случаи, различающие
правильный и ошибочный алгоритмы данного варианта.

## Платформенные ограничения

- Пособие ориентировано на MS Visual Studio 2019/2022 и Windows, а текущая
  рабочая среда - macOS.
- `Windows.h`, `SetConsoleCP`, `SetConsoleOutputCP` и `system("pause")`
  добавлять только для явно Windows-ориентированного исходника. Для
  локальной проверки переносимого консольного кода они не нужны.
- Перед созданием Windows Forms-проекта уточнить требуемый язык и
  технологию. Пособие одновременно показывает C++/CLI- и C#-подобные
  фрагменты, а приложение В прямо описывает C# Windows Forms.
- Не утверждать, что Windows Forms-приложение собрано или визуально
  проверено, если оно не запускалось в Windows и MS Visual Studio.
- Не менять `PlatformToolset` в `.vcxproj` механически по примеру
  приложения Г. Сначала определить реальную версию Visual Studio и
  установленный toolset.

## Отчеты по лабораторным

Отчет создавать или изменять только по прямой просьбе пользователя.

- Не придумывать ФИО, группу, вариант, преподавателя, дату и результаты
  запуска. Недостающие персональные данные запросить.
- Титульный лист строить по приложению А пособия, если пользователь не дал
  другой шаблон.
- Включать точную формулировку задания и варианта, требуемую расчетную
  часть, результаты тестирования, комментированный текст программы,
  заключение и список использованной литературы.
- Для ЛБ 1.1 добавить понятие табулирования и псевдокод; для ЛБ 1.2 и 1.3
  - диаграмму классов; для ЛБ 1.4 - теорию и алгоритм; для ЛБ 2.1 -
  скриншот работающего приложения; для последующих Windows Forms-работ -
  состав интерфейса, обоснование элементов и обработчики событий.
- Не вставлять вымышленные скриншоты и не выдавать подготовленный пример
  вывода за результат реального запуска.

## Критерии завершения

Работа считается проверенной, когда:

- реализация соответствует точному варианту и обязательным требованиям;
- консольный код собирается без предупреждений с указанными флагами;
- программа реально запущена на репрезентативных тестах;
- для кода с динамической памятью пройдены ASan и UBSan;
- не изменены несвязанные файлы и существующие бинарники;
- в ответе честно указаны платформенные и непроверенные части.
